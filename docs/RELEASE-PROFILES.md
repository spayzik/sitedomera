# Production и staging ДЕКОРАЙ

Требуются Node.js 24, npm и чистый checkout. На Windows для ZIP Host-A используется PowerShell 7. Подключения к внешним сервисам задаются окружением сборки и конфигурацией хостинга, а серверные ключи остаются вне Git и webroot.

## Изолированный staging

1. Выполните `npm ci` и `node scripts/build-profile.mjs staging`. Используйте только `dist/` для GitHub Pages на `/dekoray-preview/`. На всех HTML этого профиля действует `noindex, nofollow, noarchive`.
2. Для тестовой доставки укажите HTTPS-адрес отдельного `/api/lead` в `VITE_DEKORAY_STAGING_LEAD_API`. Сервер должен отвечать как staging, разрешать только origin preview, принимать код тестового доступа и синтетический контакт, иметь отдельные хранилище и получателя. Точные команды запуска и конфигурация прокси приведены в [STAGING-LEADS.md](STAGING-LEADS.md). Проверяйте отправку с согласованным тестовым кодом.
3. Для аналитики задайте отдельный `VITE_YM_STAGING_ID`. Условия включения Вебвизора и проверка визита описаны в [METRIKA.md](METRIKA.md).
4. Для проверенных публичных снимков передайте абсолютные пути через `DEKORAY_BUILD_AVITO_SNAPSHOT` и `DEKORAY_BUILD_STOCK_SNAPSHOT`. Сборка проверит формат и добавит данные. После срока годности снимок склада отображается как неизвестное наличие. Настройки и хранилище PHP размещаются отдельно от Pages.

## Production для Host-A

1. В отдельном чистом окружении выполните `npm ci`, затем `node scripts/build-profile.mjs production`. Настройте подтверждённый `VITE_YM_ID` и остальные публичные переменные до сборки. Для воспроизводимой даты YML задайте `SOURCE_DATE_EPOCH` в секундах Unix.
2. Для архива полного комплекта используйте `pwsh -File scripts/package-host-a.ps1 -OutputPath <абсолютный путь к ZIP>`. Хостинг обслуживает вложенные index.html, 404 и маршрут `/api/lead`. Выберите подтверждённый способ HTTP → HTTPS для фактической схемы Apache и TLS.
3. Разместите содержимое `web/` в document root. `api-entry/lead.php` предназначен для публичного PHP-входа. `private-runtime/`, конфигурация с credentials, БД заявок и хранилища должны быть недоступны по HTTP. `host-settings/` содержит настройки для применения администратором. Сохраните оба действующих файла `generated/*.json` и расписание их обновления.
4. Сверьте утверждённое согласие, версию и SHA-256, права и доступ к SQLite, выделенного контрагента `intakeAgentId`, получение форм менеджером, повторы доставки и сроки хранения. Запускайте автоматический повтор только после проверки на отдельном хосте с тестовым получателем.
5. После отдельного разрешения владельца опубликуйте с резервной копией и обратимой сменой файлов. На фактическом адресе проверьте 301/308, 404, canonical, robots, sitemap, фид, формы и HTTPS. Подтвердите кабинет Вебмастера и Search Console. IndexNow выполняется отдельной командой после проверки доступности файла владения: `node scripts/indexnow.mjs /изменённый-маршрут/`. Ключ задаётся через `DEKORAY_INDEXNOW_KEY` в окружении, его файл генерируется в production-сборке.

См. [MOYSKLAD-LEADS.md](MOYSKLAD-LEADS.md), [MOYSKLAD-INVENTORY.md](MOYSKLAD-INVENTORY.md) и [SEO-INDEXATION-CHECKLIST.md](SEO-INDEXATION-CHECKLIST.md).

## Предпусковая проверка Host-A

- Уточните активный тариф, фактический document root, пользователя FastCGI и CLI. Требуются PHP 8.3+ и расширения curl, pdo_sqlite, mbstring, intl, dom, openssl. Проверьте на хосте командами `php -v` и `php -m`. Те же требования действуют для PHP через веб-сервер.
- Создайте каталог runtime за пределами дерева соседних виртуальных сайтов. Установите 0700 для каталога и state, 0600 для config.json, SQLite и журналов. Проверьте, что PHP и cron работают под пользователем с доступом к state. Секреты вводятся на сервере через закрытый файл конфигурации. Сверьте все пути с конфигурацией API-входа.
- Проверьте CLI и защищённый read-only preflight на тестовом хосте. После отдельной owner-приёмки настройте `retry.php <webroot> --deliver` раз в минуту. В мониторинге храните только количество принятых, удержанных, отложенных и просроченных. Оповещайте ответственного при появлении удержанной записи.
- Подготовьте резервную копию действующего webroot, конфигурации, расписания и закрытой базы с возможностью восстановления. Для rollback верните прежние web-файлы и правила хостинга. Сохраните актуальные снимки Авито и остатков, а также журнал заявок. При возврате версии PHP остановите новый worker и сверяйте подтверждённые ID до запуска очереди.
- После проверки `mod_headers` примените настройки кэша из пакета. Хэшированные CSS/JS получают `immutable`; HTML, sitemap, YML и динамические снимки проверяются перед повторным использованием. Проверьте заголовки, HTTP → HTTPS, www, alias, 404 и недоступность закрытых файлов внешним GET. Включайте перенос HTTP на HTTPS средствами панели после подтверждения SSL. [Документация REG.RU](https://help.reg.ru/support/hosting/redirekty/redirekt-s-http-na-https-dlya-linux)
- Для проверки воспроизводимости зафиксируйте SHA source, Node/npm, конфигурацию и `SOURCE_DATE_EPOCH`. ZIP ставит одинаковую дату во все записи. Публичные текущие снимки живут на хостинге отдельно от пакета.
