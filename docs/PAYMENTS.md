# Онлайн-оплата ДЕКОРАЙ

## Сценарии сделки

1. Мгновенная оплата. Уполномоченный контур комплектации создаёт и резервирует заказ в МойСклад, подтверждает способ получения и передаёт заказ приватному издателю ссылки. Издатель проверяет состояние заказа, продавца, рублёвую валюту, резерв, комплект, цены и доставку. Покупатель оплачивает подтверждённую комплектацию на странице ЮKassa. Автоматическое создание и резервирование заказа ждут бизнес-схему и отдельный разрешённый контур МойСклад.
2. Оплата после заявки. Менеджер подтверждает наличие, количество, доставку и срок, оформляет готовый к оплате зарезервированный заказ в МойСклад и передаёт покупателю персональную ссылку из того же издателя. Исходная заявка сохраняется в действующем контуре. Разовая ссылка выдаётся оператором через согласованный канал.
3. Сайт показывает онлайн-оплату при наличии верифицированного сервером предложения. PHP рассчитывает итог в целых копейках из серверного каталога и утверждённой доставки и повторно сверяет заказ перед созданием платежа. Скидки, частичная оплата и продажа под будущий приход требуют собственного подтверждённого коммерческого и фискального сценария.

Каждому заказу МойСклад соответствует одна запись оплаты. До окончательного статуса ЮKassa менеджер сохраняет резерв и сумму. Правило распространяется на неопределённый результат запроса и применяется даже после короткого срока выдачи ссылки. Снятие резерва, создание объектов, проведение платежа в учёте и отгрузка остаются операциями согласованного процесса МойСклад. Платёжный runtime использует read-only токен для проверки уже подготовленного заказа.

## Подключение

1. В существующем PHP 8.3+ runtime разместите `api-entry/payment.php` как `api/payment.php` с маршрутами из Apache-конфигурации. Модули `payment-*.php` и `catalog-contract.json` из `private-runtime/` разместите в закрытом `dekoray-leads` вне всех webroot, рядом с PHP-контуром заявок. Нужны cURL, OpenSSL, mbstring, PDO SQLite и действующий TLS. Директория и `state/` имеют режим 0700, приватные JSON и SQLite — 0600. FastCGI должен передавать заголовок Authorization и выставлять HTTPS=on только для доверенного TLS.
2. В изолированном стенде заведите тестовый магазин ЮKassa, включите проверку чеков и задайте отдельный URL `https://<test-host>/api/payment/webhook`. События — `payment.succeeded`, `payment.canceled`, `refund.succeeded`. Checkout preview собирается только с HTTPS-адресом этого API. Разрешённый браузерный origin — `https://spayzik.github.io`. Доступ к конкретному заказу требует непрогнозируемый ключ.
3. Поместите изолированную конфигурацию в `payments-sandbox.json` в закрытом каталоге. Пара тестового Shop ID и ключа передаётся через хранилище секретов. Для production используется отдельный `payments-production.json`, отдельный Shop ID ЮKassa, отдельная БД и отдельный защищённый ключ. Сведения о продавце и кассе проверяет Owner. До их подтверждения профиль оплаты выключен.

Поля приватной конфигурации приведены без рабочих данных. Ключ `key` генерируется из 32 случайных байт в hex и сохраняется на весь срок жизни соответствующей БД. `secretKey` — ключ API ЮKassa. У sandbox ожидается префикс `test_`, у production — `live_`. Перед POST провайдеру проверяются тип, идентификатор и статус магазина по `GET /me`, после этого PHP проверяет те же ограничения при подтверждении каждого платежа.

| Поле | Значение |
|---|---|
| `enabled`, `mode`, `siteHost` | По умолчанию выключено. Режим `sandbox` — отдельный HTTPS-хост, `production` — основной домен. |
| `shopId`, `secretKey`, `key` | Shop ID, секрет провайдера, отдельный случайный ключ checkout. |
| `sellerName`, `sellerInn` | Подтверждённые реквизиты юрлица или ИП из кабинета ЮKassa, контрольная сумма ИНН проверяется. |
| `holdPolicyVerified`, `fiscalizationVerified`, `receiptScheme` | Отдельные допуски на удержание резерва и кассовую схему. Реализован одновременный платёж и чек с `full_payment` для подтверждённой передачи при расчёте. |
| `vatBySku` | Подтверждённый код НДС ЮKassa на каждый SKU. Если у позиции нет SKU, ключ — ID позиции серверного каталога. |
| `deliveryMethods` | Объект утверждённых способов, каждый с `label`, `priceMinor` и `vatCode`. Платная доставка в production требует `crmServiceId` уже включённой в заказ услуги МойСклад. |
| `saleStateId`, `rubCurrencyId`, `moySkladReadToken` | Только production. ID согласованного статуса готовности к оплате, ID RUB и выделенный read-only токен. Проверка использует утверждённую организацию и существующие соответствия `config.json`. |

Перед включением продажи подтвердите зарегистрированную кассу, соответствие реквизитов и налоговых ставок, способ доставки и момент передачи. Схема «предоплата, затем отдельный чек при передаче» требует утверждения правил второго чека и проверки в sandbox. Возвраты инициирует оператор в ЮKassa с необходимым фискальным оформлением. Входящие события и статус API отражают частичный и полный возврат. ## Выдача короткой ссылки

В доверенном процессе передайте JSON заказа в stdin `php payment-cli.php issue <document-root> <host>`. Поля `mode` (`instant` или `manager`), `crmOrderId`, `items` (массив объектов `{id, quantity}`), `deliveryId`, `receiptEmail`, `expiresAt` (Unix в секундах, до 30 минут с момента выдачи). В sandbox используйте отдельный синтетический UUID заказа и `dekoray@example.test`. На stdout возвращается персональная ссылка с ключом во фрагменте. Сохраните его только в защищённом канале выдачи заказа. По возможности передайте stdin напрямую из операционной системы. Временные файлы с контактами должны быть закрыты и удалены после использования.

Идентификатор заказа отдельный от ключа доступа. Срок для начала оплаты — до 30 минут, чтение по выданному ключу после создания платежа — до семи дней. В браузере GET /api/payment сообщает только готовность и тип среды. POST проверяет ключ в Authorization и конкретный origin. PHP принимает только `action` и при создании платежа ID уже согласованного способа получения. Цена, скидка, валюта, позиции и контакт для чека поступают из приватного заказа.

## Сверка, сбой и восстановление

- `payment-cli.php reconcile <document-root> <host>` сверяет известные незавершённые платежи, очищает зашифрованные контакты просроченных предложений и возвращает обезличенные счётчики. После подключения добавьте его в штатный cron с отдельным контролем ненулевого выхода. Контакт также стирается из платёжного журнала сразу после связывания с ответом ЮKassa.
- Начало оплаты закрепляется в SQLite до обращения к ЮKassa. Повтор отправляет тот же ключ идемпотентности и тот же состав. Повторная попытка после истечения предложения или истечения безопасного окна идемпотентности требует ручной сверки. Перед снятием резерва при неизвестном результате сопоставьте идентификатор заказа с `metadata.order_id` под подтверждённым магазином в кабинете ЮKassa.
- Webhook служит сигналом для проверки объекта через API. Сопоставляются магазин, среда, ID, RUB, сумма и идентификатор заказа. При временном сбое проверки API получает HTTP 503. Повтор подтверждённого события приводит к тому же состоянию. Фиксированный `return_url` открывает экран сверки по серверному статусу.
- Храните текущую и проверенную резервную копии платёжной SQLite. После отката к более старой БД заморозьте выдачу и начало оплаты, сверьте все записи после времени backup с реестром ЮKassa и CRM перед возобновлением. Идентификаторы ранее выданных заказов не должны использоваться повторно. Не переносите платёжный SQLite между магазинами.
- Доступ к логам и конфигурации разграничен. Provider HTTP payload, email, ключ ссылки, банковские данные и токены не включаются в отчёты или журналы приложения. В аналитике используются только стабильный публичный идентификатор заказа, цена, RUB и карточки. Событие покупки допустимо после подтверждённого статуса PHP.
